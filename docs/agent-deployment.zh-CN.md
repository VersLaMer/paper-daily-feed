# Agent 部署说明

[English](./agent-deployment.md) | [简体中文](./agent-deployment.zh-CN.md)

> 本文件是给 AI 编程 Agent 的补充指令。请替用户完成部署，并尽量最小化用户端的输入和操作。

## 部署原则

**内部模型**

Agent 应在内部遵循以下模型。除非用户主动询问，或必须理解某个概念才能作出选择，否则不要向用户复述这些具体工程实现概念：

- **Fork** 是这个项目在用户本人 GitHub 账号下的副本。只把规范仓库 <https://github.com/nehSgnaiL/paper-daily-feed> fork 到用户账号并部署；不得部署到规范仓库或 Agent 自己的账号。
- **GitHub Actions** 在这个 fork 中自动运行论文推送任务。
- **GitHub Secrets** 用于保存邮箱密码和 API key 等凭据；保存后不应再次显示其值。
- **GitHub Variables** 用于保存非敏感设置。本项目把名为 `APP_CONFIG` 的 Actions variable 作为应用配置。
- `APP_CONFIG` 是一段 JSONC 文本，即允许注释和尾随逗号的 JSON。它无需修改仓库文件，就能控制研究兴趣、论文来源、匹配、摘要和投递行为。

正常的自定义方式是更新 `APP_CONFIG`，而不是修改应用代码。Variable 的新值会在之后的工作流运行中生效，不产生 Git commit，因此 fork 可以持续跟随上游更新，不会积累用于个性化设置的提交。

**操作前规则**

- 部署前，将目标 fork 更新到当前上游版本。如果旧版个性化提交造成历史分叉，应将其实际配置迁移到 `APP_CONFIG`、GitHub Secrets 和 GitHub Variables，使 fork 与上游保持一致，并验证结果。只有缺少必要信息或预期效果将发生变化时，才让用户参与。
- 从头到尾阅读 `@README.zh-CN.md`，重点遵循 **快速开始**。如果本文件与 README 不一致，以 README 为准。
- 收集可选设置或提出配置方案前，先阅读 `@config/app.example.jsonc`。只使用当前模板确实支持的字段、值类型和行为。
- 用户有额外需求时，先判断 `APP_CONFIG` 能否满足，并优先采用最小的相关配置变更。
- 不得为了部署个性化而编辑或提交应用代码、工作流、`data/journals.config.ts` 或其他受版本控制的文件。如果需求确实无法用 `APP_CONFIG` 表达，先解释缺口，并修改受版本控制文件。
- 修改 GitHub 状态前，确认当前登录账号和目标 fork。尽量复用用户已有的 fork。
- 将部署操作尽量保留在 GitHub 端。使用 `gh`、GitHub API、仓库页面、Actions、Secrets 和 Variables 检查文件、配置、验证、更新并测试目标 fork。默认不 clone 仓库，也不要求用户进行本地设置。只有必要步骤确实没有可行的 GitHub 端路径时，才使用临时 checkout；该过程由 Agent 内部完成，不得写入凭据，使用后立即清理。
- 替用户完成页面操作、命令、保存和检查。只有会实质影响最终效果的选择、安全输入凭据、登录或二次验证需要用户亲自处理。

**信息来源与核验要求**

模型记忆和搜索结果摘要只能作为线索，不能作为证据。不得编造期刊名称、排名、ISSN、RSS 地址、配置字段、服务要求或成功结果。

- 声明项目行为或保存配置值前，必须用当前的 `@README.zh-CN.md`、`@config/app.example.jsonc`、源码或工作流文件核对。
- 通过期刊或出版社官网核对期刊身份和 ISSN；Crossref 可作为第二来源。打开 RSS 或 Atom 地址，确认它能返回该期刊可识别的条目，才可将其视为有效订阅源。
- 用户要求“Top 期刊”时，在内部确定排名来源、指标、分类和年份。用当前来源和年份简洁标注候选清单并附上来源链接；只有歧义会影响结果或用户主动询问时，才解释方法。不得把模型生成但无来源的顺序说成排名。
- 当 SMTP、Zotero、GitHub 或 API 的要求会影响部署时，使用服务商当前的官方文档核对。
- 在内部核验期刊候选项。默认只展示简洁的候选清单和用户作出选择所需的差异；事实存在不确定性、选择依赖证据或用户主动询问时，再提供详细证据链接。重要信息无法核实时，应直接说明，不得自行补全。
- 只有实际观察到结果后，才能声称检查或工作流成功。不得伪造引用、页面内容、命令输出、工作流状态或邮件送达结果。

## 执行流程

尽量减少用户投入和实现细节。只询问无法安全推断且会实质影响用户可见效果的信息；如果合并几个简短且相互独立的问题能减少用户总体操作，就一起询问。配置字段、技术默认值、迁移步骤和验证方式由 Agent 在内部决定。默认只提供面向结果的简洁总结；只有解决阻塞或用户主动询问时才提供技术细节。保持前后信息衔接，只解释用户确实需要决定的陌生选项。

1. **确认目标。** 确认用户希望收到每日论文邮件，然后询问用户所属学科。不要预先灌输实现细节。
2. **缩小研究兴趣。** 根据用户描述推断简洁的研究画像。只有实质性歧义会改变推荐结果时才追问。Agent 在内部将结果写入 `interests.profile.summary`，无需让用户审阅字段或实现措辞。
3. **选择并核验论文来源。** 在内部为已经理解的研究兴趣确定并核验合适来源。只展示简洁的推荐选择和影响用户效果的必要差异；只有多个合理选项会实质改变推送结果时才让用户选择。除非用户询问，否则将配置机制和常规证据留在内部。

   内置目录主要覆盖地理科学。地理科学用户应把确认过的期刊对应到 `data/journals.config.ts` 中的准确条目，再写入 `feeds.catalogSelections`。其他学科使用 `feeds.includeCatalog: false`，并把已核验的订阅源写入 `feeds.customRss`。空的 `catalogSelections` 表示使用全部内置期刊，不表示一个都不选。
4. **确定可选行为。** 根据用户需求和项目当前默认值，在内部推断 Zotero 辅助、AI TLDR、输出语言、推送数量和匹配严格度的合理默认设置。只询问会实质影响投递结果且仍然缺失的选择；适合时合并相互独立的问题。所需凭据通过安全输入收集。除非用户主动询问，或某个无法安全发现的值必须由用户提供，否则将服务商参数、模型标识和配置字段名留在内部。
5. **构建配置。** 根据已经理解的目标生成最小可用 `APP_CONFIG`，并对照当前 `config/app.example.jsonc` 检查每个字段。默认不展示 JSONC，也不解释字段。保存或替换前，只提供一份面向结果的简洁总结，并取得继续执行的许可。不得仅为运行本地配置检查而 clone 仓库。
6. **准备 GitHub 和凭据。** 检查 `gh`，需要时发起 GitHub 网页登录，确认账号，再查找或创建用户的 fork。只收集仍然缺失的投递信息和凭据；适合时合并询问非敏感字段。密码、授权码和 API key 只能通过安全输入收集。
7. **保存设置，不创建个性化提交。** 将凭据保存为 Actions Secrets，将审阅通过的 JSONC 保存为仓库 Actions variable `APP_CONFIG`。不得为这些设置创建或推送 commit。
8. **在 GitHub 端验证、测试和交付。** 启用所需工作流，核验自动更新，并运行 **Test paper feeds**。将这次 GitHub Actions 运行同时作为配置验证和投递测试：它会读取已保存的 `APP_CONFIG`、构建当前项目并尝试测试投递。检查非敏感日志，通过 Secrets 或 Variables 修正后重新运行，直到实际观察到成功且用户确认收到邮件。交付说明应简洁并面向结果；只有用户询问时才提供实现细节。

**部署检查清单**

- [ ] **准备 GitHub：** 确认 `gh` 可用且已登录，核对当前账号和目标 fork。
- [ ] **建立研究画像：** 明确用户期望的领域并生成最终 `interests.profile.summary`，只对实质性歧义进行追问。
- [ ] **选择论文来源：** 在内部核验期刊身份、ISSN 和可用订阅源；只有来源选择会实质影响结果时才询问用户。
- [ ] **确定可选功能：** 应用合理默认值，只补全 Zotero、AI 摘要、输出语言、推荐数量和匹配严格度中仍然缺失的用户可见选择。
- [ ] **审阅 `APP_CONFIG`：** 对照 `config/app.example.jsonc` 核验每个字段；除非用户要求，否则只展示简洁的结果摘要，不展示 JSONC。
- [ ] **保存 Secrets：** 保存必填的 `RECEIVER`、`SENDER`、`SENDER_PASSWORD`、`SMTP_SERVER`、`SMTP_PORT`，以及已启用功能确实需要的凭据。
- [ ] **保存 Variable：** 将确认后的配置保存为仓库 Actions variable `APP_CONFIG`，不得提交到 fork。
- [ ] **开启完整自动更新：** 让每周自动更新包含工作流文件。创建仅限目标 fork 的 fine-grained token，授予 **Contents** 和 **Workflows** 读写权限，并直接保存为 Actions secret `MAINTENANCE_SYNC_TOKEN`。只有 GitHub 要求登录或二次验证时才让用户参与。
- [ ] **启用工作流：** 在 fork 中启用 Actions、**Daily paper feeds**、**Repository maintenance** 和 **Test paper feeds**。
- [ ] **核验自动更新：** 运行 **Repository maintenance**，实际观察每周保活和上游同步成功，包括工作流文件。
- [ ] **验证配置与投递：** 在 GitHub 端运行 **Test paper feeds**，确认已保存的 `APP_CONFIG` 能够加载且测试投递成功。只检查非敏感日志，并通过 Secrets 或 Variables 修正设置；不得 clone 仓库或修改受版本控制的文件来强行通过测试。
- [ ] **完成交付：** 提供 fork 链接、成功测试的运行链接、每日运行状态，以及暂停 **Daily paper feeds** 的简单方法。不得重复任何凭据。

## 安全与完成条件

**保护凭据**

- 不要让用户在聊天中粘贴密码、token、授权码或 API key。凭据应通过互动式程序输入。
- 不得在命令、输出、日志、临时文件、`APP_CONFIG` 或 shell 历史中暴露凭据。
- Agent 创建的 `MAINTENANCE_SYNC_TOKEN` 只用于目标 fork 的每周自动更新，不得用于本地登录或其他项目。
- 替换已有值前，先展示并确认新的非敏感 `APP_CONFIG`。

**完成条件**

只有在清单全部完成、实际观察到维护工作流成功、实际观察到测试工作流成功，并且用户确认收到测试邮件后，才可结束部署。不得根据预期声称成功，不得削弱安全设置，也不得修改应用或工作流代码来强行通过测试。
